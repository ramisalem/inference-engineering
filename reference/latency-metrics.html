Latency metrics

The numbers that describe how fast a model feels, on one page.

Definitions

MetricDefinitionFormulaMostly driven by
TTFT
time to first token · ms		Request sent → first non-empty token receivedmeasured directlyqueueing + prefill + network
ITL
inter-token latency · ms		Average gap between consecutive tokens, first token excluded(E2E − TTFT) / (N − 1)one decode step
Decode TPS
per user · tok/s		Speed of the stream after the first token1000 / ITLmsdecode speed
E2E
end-to-end latency · ms		Request sent → last token receivedTTFT + (N − 1) × ITLeverything, including client and network
Throughput
system TPS · tok/s		Output tokens per second across all concurrent requeststotal output tokens / wall timebatching, concurrency (see Under load)

Naming in this course: say ITL, not TPOT ("time per output token", same idea). Say decode TPS for the per-user stream speed and throughput for the system total. NVIDIA's "TPS per user" is N ÷ E2E, which includes TTFT, so always state your definition.Definitions and the caveat "tool implementations vary, so compare results only when definitions align": NVIDIA, "Metrics".

Formulas you'll use constantly

TPS = 1000 ÷ ITL(ms)   ·   ITL(ms) = 1000 ÷ TPS
E2E ≈ TTFT + (N − 1) × ITL
largest affordable ITL = (deadline − TTFT) ÷ (N − 1)
per-user TPS ≈ throughput ÷ concurrent users   (if shared evenly)

Measuring honestly

  • Warm up first, unless cold start is what you're measuring. The first request may include loading the model.
  • Bust the prefix cache when measuring prefill (stream_probe.py does this by default), or measure cache hits on purpose.
  • Count tokens with the server's usage numbers, not stream chunks. A chunk isn't always exactly one token.
  • Client clock vs server clock: the gap between them is network and client overhead.
  • Report percentiles, not just means: p50, p95 and p99, with enough samples (over 100 for a real p99).
  • Write down how you measured: model, quantization, hardware, prompt and output lengths, concurrency, tool.

Under load

Latency is what one user feels; throughput is what the server delivers in total. Serving more users from the same hardware usually raises the first and lowers the second's cost per token.

TermMeaning
p50 / p95 / p99the value that 50% / 5% / 1% of requests exceed. Means hide the tail; with N requests, p99 needs N well over 100.
SLOa target written as a percentile, e.g. "95% of requests have TTFT below 200 ms"
Goodputrequests per second completed while meeting the SLO
Queueingone slot: extra requests wait. TTFT ↑↑, ITL =, throughput flat
Batchingseveral slots decode in the same step. Throughput ↑, every user's ITL ↑
Closed loopC users, each waits for its reply before sending again (--concurrency). Load backs off when the server slows: coordinated omission.
Open looprequests arrive at a set rate regardless (--rate). Like real users; shows honest tails.
Online / offline / asynca person waits now (latency) / nobody waits (throughput, cost) / a queue + webhook with a deadline
Little's law: L = λ × W   (in system = arrival rate × time in system)
queued TTFT ≈ (requests ahead) × (time per request) + own prefill
P(at least one of n calls is slower than p99) = 1 − 0.99n
